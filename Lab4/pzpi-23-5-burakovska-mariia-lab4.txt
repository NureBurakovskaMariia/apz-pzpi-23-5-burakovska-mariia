2 ЗАВДАННЯ

     В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: 
     масштабувати сервер горизонтально — багато копій сервера виконують однакові функції для різних користувачів; 
     масштабувати сервер вертикально — різні мікросервіси виконують різні функції і масштабуються окремо одне від одного.
     З технічної точки зору, масштабування можна виконати так: 
     деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів;
     деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. 
     ваш власний спосіб показати що система може масштабуватись. 
     На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система.

     3 ОПИС ВИКОНАНОЇ РОБОТИ

     Для забезпечення стабільної роботи системи управління притулками під час пікових навантажень було розроблено та імплементовано архітектуру масштабованого бекенду.
     Опис стратегії масштабування системи: Було обрано стратегію горизонтального масштабування монолітного бекенду в комбінації з кешуванням даних. Цей підхід передбачає розгортання кількох ідентичних екземплярів Node.js-сервера для паралельної обробки запитів, а також використання in-memory бази даних (Redis) для розвантаження основної реляційної бази даних PostgreSQL.
     Опис технічних рішень, які роблять масштабування можливим:
1. Контейнеризація та Оркестрація (Docker & Compose): Бекенд-застосунок запаковано в Docker-контейнер. За допомогою директиви deploy: replicas: 3 у файлі docker-compose.yml динамічно створюються три незалежні копії сервера.
2. Балансування навантаження (Load Balancer): Точкою входу в систему виступає веб-сервер Nginx. Він налаштований як Reverse Proxy і розподіляє трафік між трьома репліками Node.js за алгоритмом Round-Robin.
3. Кешування (Патерн Cache-Aside): У програмний код інтегровано взаємодію з Redis. При надходженні GET-запиту сервер спочатку перевіряє наявність даних у Redis. Якщо дані є, вони віддаються миттєво з оперативної пам'яті. У разі відсутності – сервер звертається до PostgreSQL, повертає дані клієнту та одночасно записує їх у Redis із заданим часом життя. При зміні даних (POST/PUT запити) реалізовано автоматичне очищення кешу для збереження консистентності.
     Аналіз вузьких місць системи: Під час серії навантажувальних тестів було проаналізовано зміщення "вузьких місць" інфраструктури:
1. Процесор (CPU) бекенду: При роботі одного екземпляра сервера першим вичерпувався ресурс CPU (однопотоковість Node.js). Горизонтальне масштабування вирішило цю проблему.
2. Пул підключень до БД: При масштабуванні до 3 реплік виявилося нове вузьке місце – пул з'єднань єдиної бази PostgreSQL, яка не встигала обробляти шквал одночасних транзакцій. Це призвело до появи помилок по таймауту. Впровадження Redis частково вирішило цю проблему, забравши на себе 99% навантаження на читання.
3. Ефект натовпу: При тестуванні кластера з Redis було виявлено класичну архітектурну аномалію. Оскільки навантажувальний тест миттєво імітував 200 користувачів при пустому кеші, всі три сервери одночасно не знайшли даних у Redis і синхронно звернулися до PostgreSQL. Це викликало короткочасне захлинання бази даних: максимальний час відповіді підскочив до 19.54 с, а 0.23% запитів відвалилися по таймауту. Однак, як тільки перший запит записав дані в кеш, наступні 47 тисяч запитів обробилися безпомилково. Майбутнім способом оптимізації я можу розглядати реалізацію алгоритму прогріву кешу.
     Опис навантажувальних тестів: Для імітації реального трафіку було використано інструмент k6. Сценарій генерував навантаження від 200 одночасних віртуальних користувачів протягом 30 секунд.
* Тест 1 (Один сервер без кешування): Система продемонструвала стабільність, медіанний час відповіді склав ~51.25 мс. Загальна пропускна здатність становила 1390 запитів на секунду.
* Тест 2 (3 сервери + Nginx + Redis): Завдяки розподілу навантаження та кешуванню медіанний час обробки основного масиву запитів покращився у 6 разів і склав 8.74 мс, а мінімальний час впав до 0.5 мс. Пропускна здатність кластера склала ~1293 запитів/сек. Загальна кількість оброблених запитів сягнула 47 292. Відсоток успішних перевірок склав 99.76%. Наявність 0.23% помилок успішно проілюструвала явище Cache Stampede, яке було описано вище, при холодному старті системи.
     Скріншоти результатів тестування можна знайти у Додатку Б.
     Для підготовки інфраструктури, розробки конфігураційних файлів та аналізу результатів тестування було використано сервіси штучного інтелекту. 
Назва інструменту та версія: Gemini (Google). 
     Мета використання: Створення конфігурації docker-compose.yml (Nginx, Redis, PostgreSQL), імплементація патерну Cache-Aside за допомогою бібліотеки redis у Node.js, написання скрипта навантажувального тестування (k6), а також розшифровка метрик тестування та ідентифікація проблеми "Cache Stampede". 
     Внесок автора: Автор самостійно обрав стратегію горизонтального масштабування, провів рефакторинг моделей бази даних (knexfile.js) для підтримки змінних середовища та впровадив логіку інвалідації кешу. Також автор виконав локальне розгортання кластера, провів серію навантажувальних тестів та проаналізував отримані метрики для виявлення архітектурних аномалій.
     

4 ВИСНОВКИ

     У результаті виконання лабораторної роботи було успішно масштабовано бекенд-частину системи управління притулками. Застосовано підхід горизонтального масштабування за допомогою балансувальника Nginx, а також впроваджено in-memory кешування через Redis для розвантаження основної БД. Проведені навантажувальні тести підтвердили високу ефективність обраних рішень: медіанний час обробки запиту зменшився до 8.74 мс. Водночас глибокий аналіз результатів дозволив виявити критичне для Highload-систем явище – Cache Stampede, що підкреслює важливість комплексного підходу та впровадження механізмів "прогріву кешу" у майбутньому.
